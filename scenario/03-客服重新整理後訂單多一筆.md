# S03：客服重新整理後訂單多一筆

## 工單 #1864

商品查詢已經能依條件和頁數回傳資料。客服要的頁面很簡單：看商品清單、建立商品、編輯商品、刪除商品。

第一版很快就完成了。

客服建立「USB-C 充電器」，畫面顯示成功。她按重新整理，資料庫裡多了一筆同名商品。

你把瀏覽器的 request sequence 記下來：

```text
POST /Product/Create → 200 OK，回傳商品清單 HTML
重新整理           → 瀏覽器再次送出同一個 POST
POST /Product/Create → 第二次寫入資料庫
```

問題不是資料庫沒有 unique constraint。這個操作本來就被送了兩次。

## 先改回應，再看表單

POST 成功後，瀏覽器不應該停在那個 POST response。成功的流程應該變成：

```text
POST /Product/Create → 302 Location: /Product
GET  /Product        → 200 商品清單 HTML
```

這個流程叫 Post-Redirect-Get。重新整理時，瀏覽器只會重新送出 GET，不能直接重複剛才的寫入操作。

你先把成功路徑改成 redirect。接著發現驗證失敗時不能照做。

如果商品價格是負數，POST 需要把原本填入的商品名稱和錯誤訊息留在表單上。這時直接 redirect 會換掉目前 request 的 ModelState 和輸入值，頁面只剩一個重新載入的空表單。

所以兩條路徑要分開：

- 成功：寫入後 redirect 到 GET。
- 失敗：留在目前 request，回傳原本的 ViewModel 和錯誤。

## 表單不該直接接 Entity

現在的 POST action 直接接收 Product Entity。

這讓瀏覽器可以送出表單以外的欄位，例如商品 Id、建立時間，甚至未來新增的內部欄位。Model Binding 會依 request 的欄位名稱嘗試填入物件；它不會自動知道哪些欄位是客服可以修改的。

你把建立商品的輸入拆成專用 ViewModel，只留下畫面真的允許填的欄位：

```text
ProductCreateViewModel
    商品名稱
    商品價格
```

資料庫 Entity 留在 Service 和 Repository 內部。POST 收到 ViewModel 後，再由 application code 建立 Entity。這樣輸入模型和資料庫模型不再共用同一份欄位清單。

## Model Binding 先幫你做了什麼？

客服送出的表單欄位本來都是字串。MVC 需要把它們綁定成 action 參數或 ViewModel 的欄位。

在這個過程中可能出現兩種錯誤：

- 欄位根本沒有提供。
- 有提供，但字串無法轉成目標型別，例如價格不是合法的小數。

Data Annotations 和其他 validator 也會把結果放進 ModelState。ModelState 不是只有「表單有沒有值」，它還保存 binding 和 validation 的錯誤。

因此 POST action 不能只檢查 Entity 是否建立成功，要先判斷 ModelState，再決定回 View 或繼續呼叫 Service。

## 頁面需要的不是更多 Controller code

你現在需要把商品查詢接到 Razor View。這條 request flow 先記成一張便條：

```text
瀏覽器 GET
    ↓
Routing 找到 ProductController.Index
    ↓
Controller 呼叫 ProductService
    ↓
Service 呼叫商品查詢
    ↓
ViewModel 傳給 Razor View
    ↓
HTML 回到瀏覽器
```

POST 建立商品則是反方向：

```text
HTML form
    ↓
Model Binding 建立 ProductCreateViewModel
    ↓
ModelState 驗證
    ↓
Service 建立 Product Entity
    ↓
SaveChangesAsync
    ↓
RedirectToAction
```

Controller 目前只需要處理 HTTP 邊界：收到什麼、驗證是否通過、成功要 redirect 還是失敗要回 View。資料怎麼查、Entity 怎麼建立，會在下一張工單處理。

## 表單上的安全問題

商品建立是瀏覽器送出的 POST。瀏覽器會自動帶上 cookie；如果另一個網站設法讓這個瀏覽器送出同一個 POST，伺服器可能把它當成使用者自己操作。

MVC 表單需要 Anti-Forgery token。表單 Tag Helper 可以產生隱藏欄位，POST action 再由驗證機制檢查 token。

這個 token 只處理 CSRF 風險，不負責：

- 判斷使用者有沒有登入。
- 判斷使用者能不能編輯商品。
- 驗證商品價格是否合法。
- 防止 SQL injection。

這些是不同的邊界，不能用一個安全機制包辦全部問題。

## 先讓建立流程可用

現有 ProductMvc sample 的建立 action 保留兩個分支：

```text
ModelState 不合法
    → return View(model)

ModelState 合法
    → 呼叫 service 建立商品
    → TempData 留下成功訊息
    → RedirectToAction(nameof(Index))
```

建立頁面的責任也很窄：

```text
商品名稱輸入框
商品價格輸入框
欄位錯誤訊息
表單送出按鈕
取消並回到清單的連結
```

Razor 只負責產生 HTML。`asp-for`、`asp-action` 和 `asp-validation-for` 這類 Tag Helper 會在 server render 階段產生欄位名稱、URL 和驗證訊息。它們不是前端元件，也不會替伺服器做最後的驗證。

頁面修好後，客服重新整理只會得到商品清單，重複建立的問題消失。

## 還沒處理完的地方

商品頁現在能建立資料，但 ProductController 已經開始同時處理：

- 路由和表單。
- ModelState。
- 商品查詢。
- 商品建立。
- 商品編輯。
- 商品刪除。

下一個需求是「建立訂單時套用客戶折扣，並呼叫運費服務」。如果繼續把規則塞進 Controller，下一次修改會先碰到另一個問題：這個 Controller 已經很難測了。

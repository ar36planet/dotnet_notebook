# S03：客服重新整理後訂單多一筆

## 工單 #1864

商品搜尋已經能把條件、投影和分頁留在資料庫。客服現在需要一個商品維護頁：看清單、建立、編輯、刪除。

第一版上線測試。

客服建立「USB-C 充電器」，畫面顯示成功。她按瀏覽器重新整理，資料庫多了一筆同名商品。

你先開瀏覽器的 Network tab，沒有先改 Controller。

```text
POST /Product/Create → 200 OK，回傳商品清單 HTML
重新整理           → 瀏覽器再次送出同一個 POST
POST /Product/Create → 第二次寫入資料庫
```

這裡有三個可能方向：

```text
A. 儲存成功後把按鈕停用，避免使用者連按。
B. POST 成功後不要直接回頁面，改成 redirect 到清單。
C. 建立動作改成回傳 204，讓瀏覽器自己決定下一頁。
```

A 可以處理連按，處理不了重新整理。C 比較像 API client 的回應，客服現在用的是 server-rendered MVC 頁面。這張工單先選 B，但還要處理失敗的情況。

## redirect 不是所有路徑都能用

你先把成功和失敗都改成 redirect。

價格填成負數後，瀏覽器的結果變成：

```text
POST /Product/Create → 302 /Product/Create
GET  /Product/Create  → 空白表單
```

剛才填的商品名稱不見了，欄位錯誤也不見了。

這時才需要看 ModelState。表單送進 MVC 時，欄位不只是「有值或沒值」；MVC 還要做字串轉型和 validation。負數價格是 validation error，文字無法轉成 decimal 也會是 binding error。這些結果都存在目前 request 的 ModelState 裡。

redirect 會開始一個新的 GET request。原本的 ModelState 和使用者填入的值不會自動跟過去。

所以目前的選擇改成：

```text
驗證失敗 → 在同一個 request 回原本的 ViewModel
儲存成功 → redirect 到商品清單
```

這不是固定的 MVC 儀式。它是因為兩條路徑需要保存的東西不同。

## 表單又讓資料庫欄位露出來

你把 GET 和 POST action 打開。

POST 直接接收 Product Entity。瀏覽器雖然只顯示商品名稱和價格，request 仍然可以額外送出商品 Id、建立時間或其他同名欄位。Model Binding 不會替這個 Entity 判斷哪些 property 是客服被允許修改的。

現在有三個選擇：

```text
A. 繼續綁 Entity，再用 Bind attribute 限制欄位。
B. 建立 ProductCreateViewModel，只放建立商品允許輸入的欄位。
C. 繼續收 Entity，在 Service 裡把不允許欄位改回去。
```

A 可以用，但欄位清單散在 binding 設定；C 要記得每個新欄位都不能被漏掉。這個畫面有 Create、Edit 兩種不同輸入，而且 Entity 還要對應資料庫，先選 B。

ViewModel 不是多包一層而已。它把「這個頁面現在允許使用者送什麼」寫成一份明確的輸入契約。

## 先讓輸入模型承擔它該承擔的事

建立商品只需要兩個欄位。商品 Id、建立時間和內部狀態不屬於這張表單。

```csharp
using System.ComponentModel.DataAnnotations;

public sealed class ProductCreateViewModel
{
    [Required(ErrorMessage = "請輸入商品名稱。")]
    [StringLength(120, ErrorMessage = "商品名稱不能超過 120 個字。")]
    public string Name { get; set; } = string.Empty;

    [Required(ErrorMessage = "請輸入價格。")]
    [Range(0.01, 100000, ErrorMessage = "價格必須介於 0.01 到 100,000。")]
    public decimal Price { get; set; }
}
```

這些 attribute 只處理輸入格式和欄位規則。商品編號不能重複、使用者能不能建立商品、庫存是否足夠，仍然要在 Service 或資料庫邊界檢查。

## MVC action 先只處理 HTTP

目前建立流程可以縮成兩個 action：

```csharp
[HttpGet]
public IActionResult Create()
    => View(new ProductCreateViewModel());

[HttpPost]
[ValidateAntiForgeryToken]
public async Task<IActionResult> Create(
    ProductCreateViewModel model,
    CancellationToken cancellationToken)
{
    if (!ModelState.IsValid)
    {
        return View(model);
    }

    await service.CreateAsync(
        new CreateProductCommand(model.Name, model.Price),
        cancellationToken);

    TempData["Message"] = "商品已建立。";
    return RedirectToAction(nameof(Index));
}
```

這段 code 沒有把資料庫 Entity 當成表單輸入，也沒有在 Controller 裡計算商品規則。Controller 只處理：

- request 要進哪個 action。
- ModelState 是否能繼續。
- Service 完成後回 View 或 redirect。

`CreateProductCommand` 是 application 內部使用的命令。它和頁面 ViewModel 可以相同，也可以不同；當輸入需求和 use case 規則開始分開時，拆開會比較清楚。

## View 只需要把錯誤放回欄位

建立頁面使用 Tag Helpers 產生欄位名稱、表單 action 和 validation message：

```cshtml
@model ProductCreateViewModel

<form asp-action="Create" method="post">
    <div asp-validation-summary="ModelOnly"></div>

    <label asp-for="Name"></label>
    <input asp-for="Name" />
    <span asp-validation-for="Name"></span>

    <label asp-for="Price"></label>
    <input asp-for="Price" />
    <span asp-validation-for="Price"></span>

    <button type="submit">儲存</button>
</form>
```

這些 Tag Helpers 在 server render 階段產生 HTML。client-side validation 可以讓畫面早一點提示，但不能取代 server-side validation；request 可以來自關掉 JavaScript 的瀏覽器，也可以來自其他 HTTP client。

## Anti-Forgery 處理的是另一種問題

這個 MVC 頁面通常使用 cookie。瀏覽器會自動帶 cookie，別的網站也可能想辦法讓它送出一個 POST。

Anti-Forgery token 讓伺服器能檢查這次表單是否由同源頁面產生。它不負責判斷：

- 使用者是不是登入者。
- 使用者能不能編輯這個商品。
- 商品價格是不是合法。
- SQL 查詢是不是安全。

這些分別屬於 authentication、authorization、validation 和資料存取邊界。

```text
已完成：

1. 建立商品成功後使用 POST → redirect → GET。
2. 驗證失敗時保留原本的 ViewModel 和 ModelState。
3. 建立表單改用專用 ViewModel，避免 overposting Entity。
4. 表單加上 Anti-Forgery 保護。
5. 商品清單繼續使用 S02 已完成的資料庫端查詢。
```

商品頁現在可以交給客服使用。下一個需求不是新頁面，而是建立訂單時套用客戶折扣、查庫存、取得運費，再寄出確認信。OrderController 已經開始接近一個不容易測的形狀。

# S01：第一張工單不是功能，是時間

## 工單 #1842

```text
客服回報：

訂單 SO-20260915-1001 是昨天晚上 8 點建立的。
今天早上在稽核畫面看到的是凌晨 4 點。
另外，客戶電話顯示空白，但客服不確定那是客戶沒填，
還是有人把原本的電話清掉了。
```

你先查訂單紀錄。

客服畫面：

| 欄位 | 值 |
| --- | --- |
| 訂單編號 | SO-20260915-1001 |
| 建立時間 | 2026-09-15 20:00 |
| 客戶電話 | 空白 |

稽核服務的記錄：

| 欄位 | 值 |
| --- | --- |
| 訂單編號 | SO-20260915-1001 |
| 建立時間 | 2026-09-16 04:00 |
| 客戶電話 | `null` |

第一個直覺是前端格式化錯了。

你把畫面顯示邏輯翻了一遍，沒有找到多加八小時的地方。接著看 API 回應，時間欄位只有：

```text
2026-09-15 20:00:00
```

沒有 `Z`，也沒有 `+08:00`。

這就不是畫面問題了。API 傳出去的資料根本沒有說明這個時間屬於哪個時區。

## 先試一個看起來合理的修正

舊系統把資料讀成沒有指定時區的 `DateTime`。

你先試著把它標成 UTC：

```text
原始值：2026-09-15 20:00:00
標記後：2026-09-15 20:00:00 UTC
```

再轉成台北時間，結果變成：

```text
2026-09-16 04:00:00 +08:00
```

問題還在。

因為「指定這個值是 UTC」只是在替原本的數字貼標籤，不會把 20:00 轉成另一個時間。原始資料如果其實是台北時間，這個修正反而把錯誤說法固定下來。

這裡需要先分清楚三件事：

- UTC 是全球共用的時間基準。
- offset 是某個時間相對 UTC 的差，例如 `+08:00`。
- time zone 是一套包含地區規則的資料，例如台北或紐約。

訂單建立時間代表「某個事件發生的瞬間」，不能只保存一組沒有上下文的時鐘數字。這種欄位需要帶著 offset，或明確以 UTC 表示。

你用固定資料做了一次測試：

```csharp
using System.Globalization;

var localInput = new DateTime(
    2026, 9, 15, 20, 0, 0, DateTimeKind.Unspecified);

var treatedAsUtc = new DateTimeOffset(
    DateTime.SpecifyKind(localInput, DateTimeKind.Utc));

var correctEventTime = new DateTimeOffset(
    2026, 9, 15, 20, 0, 0, TimeSpan.FromHours(8));

Console.WriteLine(
    $"錯誤顯示：{treatedAsUtc.ToOffset(TimeSpan.FromHours(8)).ToString("O", CultureInfo.InvariantCulture)}");

Console.WriteLine(
    $"正確 UTC：{correctEventTime.ToUniversalTime().ToString("O", CultureInfo.InvariantCulture)}");
```

輸出：

```text
錯誤顯示：2026-09-16T04:00:00.0000000+08:00
正確 UTC：2026-09-15T12:00:00.0000000+00:00
```

如果原始資料確定是台北時間，應該先用 `+08:00` 解讀，再轉成 UTC 儲存或傳輸。

你把第一個決定寫進工單：

```text
事件時間：使用明確的 DateTimeOffset 語意。
儲存與跨服務傳輸：使用 UTC。
只代表日期的欄位：另行使用 DateOnly，不塞進事件時間。
```

這張工單本來只是修時間，現在多了一個資料模型問題。

## `null` 不是「空白」

客服說客戶電話是空白。

資料庫回傳的卻是 `null`。

畫面顯示空白很簡單，但更新時就不一樣了。

客服編輯使用者資料時，可能有三種意思：

| 輸入狀態 | 可能的意思 |
| --- | --- |
| 沒有送出電話欄位 | 不修改原本的電話 |
| 明確送出 `null` | 清除電話 |
| 送出空字串 | 輸入無效，或清除電話 |

如果輸入模型只有一個可為空的字串，這三種狀態會被壓成兩種：

```text
有字串
null
```

`string?` 只能說明「這個值可能是 null」，不能說明「欄位有沒有出現」。

這是兩個不同層次的問題：

- 型別層：這個值允不允許是 null。
- 業務層：沒有提供、明確清除、輸入空字串，分別代表什麼。

所以不能只靠 nullable 標註解決更新語意。這裡先不急著設計完整 PATCH 格式，工單上留下決定：

```text
使用者電話的更新規則不能只靠 string? 表達。
後續要用明確的更新操作，或帶欄位存在狀態的輸入模型。
```

## 資料庫 Entity 也暴露太多東西

你繼續看訂單模型。

目前的作法是同一個型別同時拿來：

- 對應資料庫資料。
- 接收編輯輸入。
- 回傳 API。
- 顯示訂單清單。

這讓所有欄位都必須對所有用途開放。

訂單編號建立後不應該任意更換，建立時間也不應該由表單重新提交。可是如果整個物件都是公開 setter，HTTP request 綁定時就可能把這些欄位一起改掉。

你差點直接把這個型別改成 record，因為 record 寫起來比較短，也自帶內容相等判斷。

但訂單不是只靠內容辨認。

兩張內容完全相同的訂單，仍然是兩筆不同的訂單。訂單有自己的編號、狀態和生命週期。這種資料需要的是 Entity identity，使用 class 比較符合語意。

訂單清單上的摘要則不同。清單只需要顯示訂單編號、明細數量與總金額，不需要讓呼叫端修改資料庫 Entity。這種查詢結果可以使用 record DTO。

判斷方式不是「record 比 class 新」，而是先問：

> 這個型別的身分來自資料內容，還是來自它本身？

- 物件本身有身分，狀態會變：class。
- 主要靠欄位內容表示資料：record。
- 很小、以值複製為主的值物件：才考慮 record struct。

## 先把可以確定的邊界寫出來

你開了一個 scratch console，先不接資料庫，只確認模型的語意。

```csharp
using System.Globalization;

var localInput = new DateTime(
    2026, 9, 15, 20, 0, 0, DateTimeKind.Unspecified);

var treatedAsUtc = new DateTimeOffset(
    DateTime.SpecifyKind(localInput, DateTimeKind.Utc));

var correctEventTime = new DateTimeOffset(
    2026, 9, 15, 20, 0, 0, TimeSpan.FromHours(8));

Console.WriteLine(
    $"錯誤顯示：{treatedAsUtc.ToOffset(TimeSpan.FromHours(8)).ToString("O", CultureInfo.InvariantCulture)}");

Console.WriteLine(
    $"正確 UTC：{correctEventTime.ToUniversalTime().ToString("O", CultureInfo.InvariantCulture)}");

var order = new Order
{
    OrderNumber = "SO-20260915-1001",
    CustomerId = Guid.Parse(
        "11111111-1111-1111-1111-111111111111"),
    CreatedAt = correctEventTime,
    Items =
    [
        new OrderItem("CHG-65W", 2, 890m),
        new OrderItem("KBD-ERG", 1, 1490m)
    ]
};

var summary = new OrderSummary(
    order.OrderNumber,
    order.Items.Sum(item => item.Quantity),
    order.Items.Sum(item => item.Quantity * item.UnitPrice));

var itemsByCode = order.Items
    .ToDictionary(item => item.ProductCode);

Console.WriteLine(
    $"{summary.OrderNumber} | 數量 {summary.ItemCount} | 金額 {summary.TotalAmount.ToString("0.00", CultureInfo.InvariantCulture)}");

Console.WriteLine(
    $"KBD-ERG：{itemsByCode["KBD-ERG"].Quantity} 件");

public enum OrderStatus
{
    Pending,
    Paid,
    Cancelled
}

public sealed class Order
{
    public required string OrderNumber { get; init; }

    public required Guid CustomerId { get; init; }

    public OrderStatus Status { get; private set; }
        = OrderStatus.Pending;

    public required DateTimeOffset CreatedAt { get; init; }

    public required IReadOnlyList<OrderItem> Items { get; init; }
}

public sealed record OrderItem(
    string ProductCode,
    int Quantity,
    decimal UnitPrice);

public sealed record OrderSummary(
    string OrderNumber,
    int ItemCount,
    decimal TotalAmount);
```

輸出：

```text
錯誤顯示：2026-09-16T04:00:00.0000000+08:00
正確 UTC：2026-09-15T12:00:00.0000000+00:00
SO-20260915-1001 | 數量 3 | 金額 3270.00
KBD-ERG：1 件
```

這裡有幾個決定值得留下來。

`required` 處理的是建立時一定要有的資料。`init` 允許在建立期間設定，但建立完成後不能從外部重新指定。`private set` 則讓狀態可以改變，但修改權留在 Entity 裡面。

這些功能只是在縮小錯誤範圍。它們不能取代輸入驗證，也不能保證外部 JSON 一定符合業務規則。

`IReadOnlyList<OrderItem>` 只公開清單的讀取能力，不代表底層物件深層不可變。這是 API 邊界的選擇，不是安全複製。

`Dictionary` 是因為這裡真的需要依商品編號查找明細。若只是依序顯示，清單就夠了。

`OrderItem` 在這個 scratch 範例中是資料記錄。後續接上 EF Core 時，還要根據它是否需要獨立主鍵、變更追蹤與資料庫關聯，重新判斷它要不要成為 Entity。

## 工單先這樣結案

時間顯示已經找到原因，但舊資料不能全部自動修正。

如果資料庫裡只有「2026-09-15 20:00:00」，沒有時區資訊，程式無法單靠這個數字知道它原本是台北時間、UTC，還是其他地區時間。歷史資料需要依舊系統部署地點、寫入規則或稽核紀錄判斷。

這張工單最後留下：

```text
已確認：

1. 訂單事件時間改用明確的 DateTimeOffset 語意。
2. 舊資料的時區需另外確認，不能直接用 SpecifyKind 全部標成 UTC。
3. 訂單 Entity 與 API 回應拆開。
4. 建立時間、客戶編號、訂單編號不接受外部任意修改。
5. 客戶電話的「未提供」與「清除」留給更新 API 工單處理。

下一張工單：

商品搜尋頁在資料量增加後變得很慢。
```

# 情境式／故事任務導向教材規劃

這是第二套教材。原本的標準教材、原有範例與原本的閱讀順序都保留不動；本資料夾只放另一條學習入口。

## 故事主線

星港公司有一套運作多年的內部訂單系統。舊模組使用 Web Forms，客服、倉儲與財務共用 SQL Server。新需求不允許一次重寫，團隊因此用 ASP.NET Core MVC 逐步接手新功能。

核心資料先固定在 Users、Products、Orders、OrderItems。Redis、RabbitMQ、容器與 Kubernetes 只在工單真的遇到對應問題時才加入。

每個情境章不是獨立課堂，而是一張接著一張的工單：

需求或事故 → 先查現象 → 嘗試修正 → 發現下一個問題 → 引入必要技術 → 留下決定與未完成工作

不把人物對話當成講義，也不為了故事加入與技術無關的劇情。

## 寫作規則

- 從工單、log、資料差異、測試失敗或部署現象開始。
- 讀者先遇到問題，不先看到技術定義。
- 主角可以猜錯；錯誤嘗試要能合理地導向下一個問題。
- 技術說明只處理當下決策需要的範圍，完整定義與 API 清單回到原教材。
- MVC 是主要使用者介面；Web API 只在整合、測試、外部服務與事件處理出現。
- 不設計固定人物對話來講解技術。
- 不加入 Java 前置教學。
- 每章保留一項已完成決定與下一張未完成工單，讓整套教材保持連續。
- 章末加入原教材對照，但不寫成傳統的本章總結。

## 原教材對照標記

- 完整帶過：本章需要的核心概念在工單中講清楚。
- 透過任務帶過：讀者能完成目前任務，但完整 API 與邊界要回原教材。
- 留給原教材：只留下出場理由與閱讀位置，不在故事中展開。

## 實作與發布

新教材預計放在 scenario/。它不在 Quartz 的 ignorePatterns 內，會被遞迴建置；examples/ 仍維持原本的排除設定。

新教材若需要完整可執行專案，另放在 examples/ScenarioOrderDesk/，不修改原有範例。每個故事中的故障版本先在 scratchpad 驗證，repo 只保留可重現的正式版本。

原本的 index.md 不在這一階段修改。新教材頁面會有自己的 scenario 路徑；是否在標準教材首頁加入入口，另行決定。

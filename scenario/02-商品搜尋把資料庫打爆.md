# S02：商品搜尋把資料庫打爆

## 工單 #1857

客服要一個商品搜尋頁：輸入商品編號前綴，只看上架中的商品，每頁最多 20 筆。

測試資料只有四筆。關鍵字輸入 `CHG`，畫面顯示兩筆，結果是對的。

問題是在資料庫 log 裡。

```text
SELECT "p"."Id", "p"."DisplayName", "p"."IsListed",
       "p"."ProductCode", "p"."UnitPrice", "p"."UpdatedAt"
FROM "Products" AS "p"
```

沒有 WHERE，也沒有 LIMIT。

API 先載入四筆，再從記憶體篩成兩筆：

```text
先載入筆數：4
記憶體篩選後筆數：2
```

測試資料太小，頁面看不出差異。商品表一旦變大，API 會先把不需要的資料搬回 process，資料庫和 API 都得處理完整資料集。

## 先停在這裡

這張工單有三個方向：

```text
A. 先把全部商品載入，再用 C# 篩選。
B. 保持可組合的資料庫查詢，讓條件和分頁留在資料庫。
C. 直接改成 raw SQL。
```

A 已經是目前的做法，結果正確，但資料量一大就會浪費資源。

C 不一定錯。若 LINQ 無法表達查詢，或 DBA 需要維護一段明確的 SQL，它有使用時機；這張工單的條件很普通，先引入 raw SQL 只會多一個需要維護和參數化的邊界。

目前先選 B。接下來要確認的是：篩選、排序和分頁在什麼時候還是資料庫工作。

## 第一個修正

原本的程式先呼叫 `ToListAsync`：

```text
資料庫 → 全部 Products → ToListAsync
                         ↓
              Where → Select → Take
```

你把 `ToListAsync` 往後移：

```text
資料庫 → Where → Select → Take → ToListAsync
```

這次先不討論任何最佳化，只看執行邊界。`ToListAsync` 一旦執行，查詢就已經送到資料庫，回來的是一份記憶體清單。後面的 LINQ 不可能再改變剛才已經送出的 SQL。

## 為什麼同樣的 Where，位置不同就不一樣？

你回頭看兩個變數的型別。

`IEnumerable<Product>` 只表示可以列舉一組 Product。來源如果是已經 materialize 的 List，後面的 LINQ 會由 .NET 在記憶體執行。

`IQueryable<Product>` 表示查詢還能繼續組合，provider 可以讀取它的 expression tree。EF Core 會把可翻譯的部分轉成資料庫查詢。

兩個介面都可能延遲執行，但延遲的對象不同：

- `IEnumerable` 延後的是記憶體中的列舉。
- `IQueryable` 延後的是 provider 查詢。

所以看到 LINQ method 不夠。要一起看來源型別和開始列舉的那一行。

通常會觸發 EF Core 查詢的地方包括 `ToListAsync`、`FirstAsync`、`AnyAsync`、`CountAsync`，以及開始列舉查詢結果的操作。`ToQueryString` 只用來查看 SQL，不會替你執行查詢。

## 第二個修正：先把 query 留在可組合的型別

你先把條件和排序寫進一個 query：

```csharp
IQueryable<Product> query = db.Products.AsNoTracking();

query = query.Where(product => product.IsListed);

if (!string.IsNullOrWhiteSpace(keyword))
{
    var prefix = keyword.Trim();
    query = query.Where(product =>
        product.ProductCode.StartsWith(prefix));
}

pageSize = Math.Clamp(pageSize, 1, 50);

var rowsQuery = query
    .OrderByDescending(product => product.Id)
    .Select(product => new ProductListItem(
        product.ProductCode,
        product.DisplayName,
        product.UnitPrice))
    .Take(pageSize);

var rows = await rowsQuery.ToListAsync(cancellationToken);
```

這裡特別寫成 `IQueryable<Product>`，不是為了讓程式看起來正式。

你一開始用 `var` 宣告 query，先加了 `OrderByDescending`，變數就被推成排序後的型別。接著想再把它指派回 `Where` 的結果，編譯器會拒絕，因為變數的靜態型別已經比你想要的查詢型別窄。

先用 `IQueryable<Product>` 表達「這個變數會持續組合查詢」，反而更容易看出這段 code 的意圖。

`AsNoTracking` 是另一個決定。這個清單只讀取商品摘要，沒有要把 Entity 改回資料庫，不需要 change tracker 保存每個物件的狀態。

`Select` 也不是最後才做的格式轉換。它決定查詢需要哪些欄位。頁面只要商品編號、顯示名稱和單價，就不需要先把完整 Entity graph 載入記憶體。

## 查一次真的送出了什麼

SQLite scratch project 放入四筆固定資料，關鍵字是 `CHG`，頁面大小是 2。

修正後的 `ToQueryString()` 輸出：

```text
.param set @p 2

SELECT "p"."ProductCode", "p"."DisplayName", "p"."UnitPrice"
FROM "Products" AS "p"
WHERE "p"."IsListed" AND "p"."ProductCode" LIKE 'CHG%'
ORDER BY "p"."Id" DESC
LIMIT @p
```

結果：

```text
CHG-100W | USB-C 充電器 100W | 1290.00
CHG-65W | USB-C 充電器 | 890.00
```

這段 SQL 是 SQLite provider 的實際輸出，不直接當成 SQL Server 語法範本。要確認的事情是另一個：條件、欄位、排序和筆數都在 materialization 前交給 provider 處理。

換成 SQL Server provider 後，仍然要重新查看 generated SQL 和 execution plan。不能因為 SQLite 產生了 `LIKE`，就跳過 SQL Server 的查詢計畫驗證。

## 查詢結果正確，頁面還是變慢

商品清單修好後，客服要求在使用者清單旁顯示每個人的最近一張訂單。

你找到一段新的 code。它先載入使用者，接著在迴圈裡查訂單。

```text
查詢 Users
查詢 User 1 的 Orders
查詢 User 2 的 Orders
查詢 User 3 的 Orders
⋯
```

如果頁面列出 30 位使用者，這個形狀就是一次 parent query 加 30 次 child query。這不是 benchmark 數字，是查詢次數的結構；使用者數量變成多少，後面的查詢就可能跟著增加多少。

又要做選擇：

```text
A. 保留迴圈，每筆使用者各查一次。
B. 用 Include 載入整個關聯資料。
C. 直接投影出頁面真正需要的訂單欄位。
D. 先把所有資料載入記憶體，再由 C# 配對。
```

A 讓 query count 跟資料筆數一起長。D 只是把問題從資料庫搬到 API process。

B 可以是合理方案，但如果頁面只要最近一張訂單，載入整個 orders collection 會多拿資料；關聯資料多時，還要面對 tracking 和 SQL row shape 的成本。

這個頁面目前選 C。讀取模型需要的是一組明確的結果，不是完整的 Entity graph。projection、Include、split query 不是固定的好壞排序，要看頁面需要的資料形狀和 SQL 實際產生幾條查詢。

## 又一個邊界：AsEnumerable

你為了使用一個只有 C# 才有的格式化方法，在 query 中間加了 `AsEnumerable`。

從那一行開始，後面的 LINQ 會切到 LINQ to Objects。這個方法本身不一定錯；前面的資料如果已經用條件和分頁縮小，它可能是合理的最後一步。

問題是不能忘記資料已經跨過邊界：

```text
IQueryable
    → Where、Select、Take
    → AsEnumerable
    → C# 計算或格式化
```

如果在篩選前就切到 `IEnumerable`，後面所有工作都在 API process 做。自訂 method 也不一定能翻成 SQL；expression 放在哪裡、provider 支援什麼，會決定查詢是成功翻譯、在執行時失敗，還是被迫拉回記憶體。

## 工單交接

這張工單的驗收記錄：

```text
已完成：

1. 商品篩選、投影、排序和分頁留在 IQueryable。
2. ToListAsync 成為明確的資料庫執行邊界。
3. 只讀清單使用 AsNoTracking 和 DTO projection。
4. 查使用者與訂單時，移除迴圈內逐筆查詢的 N+1 形狀。
5. generated SQL 已在 SQLite scratch project 驗證；SQL Server provider 仍要另看實際 SQL 和 plan。
```

商品搜尋頁現在可以交給 MVC 頁面使用。客服接著回報：建立商品後按重新整理，商品會多一筆。

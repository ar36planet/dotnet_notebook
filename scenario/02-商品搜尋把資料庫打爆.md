# S02：商品搜尋把資料庫打爆

## 工單 #1857

S01 的訂單時間先記下來了。接著輪到商品清單。

客服要一個很普通的功能：輸入商品編號前綴，只看上架中的商品，每頁顯示 20 筆。

目前商品表只有 4 筆資料，頁面看起來沒有問題。你打開資料庫 log，先看到的是：

```text
先載入筆數：4
記憶體篩選後筆數：2
```

兩筆結果是對的。

但 log 裡的 SQL 沒有 WHERE，也沒有 LIMIT。程式先把 4 筆資料全部讀回來，後面才篩選。現在資料少，差別看不出來；商品表從 4 筆長到 400 萬筆時，這段程式會先把不需要的資料搬進 API process。

你先把問題縮小成一句話：

> 篩選和分頁到底是在資料庫做，還是在記憶體做？

## 第一次改動：把 `ToList` 往後移

原本的查詢流程是：

```text
資料庫 → 全部 Products → ToList → Where → Select → Take
```

`ToList` 已經把查詢執行掉了。後面的 `Where`、`Select` 和 `Take` 都只能處理記憶體裡的清單。

你把流程改成：

```text
資料庫 → Where → Select → Take → ToList
```

這次 `ToList` 之前只是在組合查詢，真正執行延後到最後。這個差異看起來只是一行的位置，實際上改變了資料傳輸量、記憶體用量和資料庫要處理的工作。

## 先確認查詢的型別

這裡有兩種看起來很像的資料來源。

`IEnumerable<Product>` 表示「可以逐筆列舉的 Product」。如果來源是已經載入的 List，LINQ 會在 .NET 記憶體中執行。

`IQueryable<Product>` 表示「還可以繼續組合、由 provider 解讀的查詢」。EF Core 會把查詢表達成 expression tree，再把能翻譯的部分交給資料庫 provider。

兩者都可能延遲執行，但延遲的工作不一樣：

- `IEnumerable` 延後的是記憶體中的列舉。
- `IQueryable` 延後的是 provider 查詢，最後才可能送出 SQL。

所以不能只看 method 名稱判斷哪裡查資料庫。要看來源型別，以及哪一行讓它開始列舉。

會觸發資料庫查詢的通常是 `ToListAsync`、`FirstAsync`、`AnyAsync`、`CountAsync`，或開始列舉查詢結果的動作。`ToQueryString` 只拿來檢查 SQL，不會執行查詢。

## 把查詢留在資料庫

你先把查詢方法放在能接觸 DbContext 的位置，讓篩選、排序、投影和分頁留在同一條 `IQueryable` 上：

```csharp
public async Task<IReadOnlyList<ProductListItem>> SearchAsync(
    string? keyword,
    int pageSize,
    CancellationToken cancellationToken)
{
    IQueryable<Product> query = db.Products.AsNoTracking();

    query = query.Where(product => product.IsListed);

    if (!string.IsNullOrWhiteSpace(keyword))
    {
        var prefix = keyword.Trim();
        query = query.Where(product =>
            product.ProductCode.StartsWith(prefix));
    }

    pageSize = Math.Clamp(pageSize, 1, 50);

    return await query
        .OrderByDescending(product => product.Id)
        .Select(product => new ProductListItem(
            product.ProductCode,
            product.DisplayName,
            product.UnitPrice))
        .Take(pageSize)
        .ToListAsync(cancellationToken);
}
```

這裡的 `IQueryable<Product>` 宣告不是裝飾。它讓變數的型別保持在可以繼續組合的查詢 abstraction，也避免前面加了排序後，變數被推成只能代表排序結果的較窄型別。

`AsNoTracking` 適合只讀的清單。這裡只回傳投影後的資料，也沒有要把商品 Entity 改回資料庫，不需要 change tracker 幫忙記錄每個物件的狀態。

`Select` 放在 `Take` 前後要看需求。這個頁面只需要三個欄位，提早投影可以讓 SQL 只選需要的資料；排序欄位則要留下來，確保資料庫能正確完成排序。

## 查一下真正送出去的 SQL

這次用 SQLite scratch project 放入四筆固定資料，關鍵字是 `CHG`，頁面大小是 2。錯誤寫法的查詢是：

```text
SELECT "p"."Id", "p"."DisplayName", "p"."IsListed",
       "p"."ProductCode", "p"."UnitPrice", "p"."UpdatedAt"
FROM "Products" AS "p"
```

輸出：

```text
先載入筆數：4
記憶體篩選後筆數：2
```

修正後的 `ToQueryString()` 輸出：

```text
.param set @p 2

SELECT "p"."ProductCode", "p"."DisplayName", "p"."UnitPrice"
FROM "Products" AS "p"
WHERE "p"."IsListed" AND "p"."ProductCode" LIKE 'CHG%'
ORDER BY "p"."Id" DESC
LIMIT @p
```

結果：

```text
CHG-100W | USB-C 充電器 100W | 1290.00
CHG-65W | USB-C 充電器 | 890.00
```

這段 SQL 是 SQLite provider 的輸出，不能直接當成 SQL Server 的語法範本；可以確定的是查詢邊界已經改對：條件、欄位、排序和筆數都在 materialization 前交給資料庫處理。換成 SQL Server provider 後，仍要重新看 generated SQL 和 execution plan。

## 又找到一個問題：每一筆明細都再查一次

商品清單修好後，客服要求在使用者頁面顯示最近一張訂單。

你看到另一段程式：先查出使用者，再逐一查每個人的訂單。頁面列出 30 位使用者時，這個查詢形狀會是一次 parent query，再加 30 次 child query。

這就是 N+1：一個查詢取得 N 筆父資料，迴圈裡又為每一筆父資料發出一個子查詢。

問題不在於 `foreach` 本身，而在於資料存取的邊界放在迴圈裡。後續要依需求改成 projection、批次查詢、合理的 Include 或 split query；不能只在外面加一層快取就當成查詢設計完成。

## 另一個容易誤判的邊界

如果在 query 中間呼叫 `AsEnumerable`，後面的運算會切換成 LINQ to Objects。若此時資料還沒有足夠縮小，後面的篩選、排序或自訂方法都會在 API process 執行。

自訂 C# method 也不是一定能翻成 SQL。EF Core 能不能翻譯，取決於 provider 和 expression 的位置；翻譯失敗時，查詢可能在執行階段拋出例外。不能因為 lambda 看起來像一般 C# 就假設資料庫能執行它。

目前的判斷順序留在工單上：

```text
1. 先確認來源是 IEnumerable 還是 IQueryable。
2. 找出哪一行開始列舉或 materialize。
3. 在資料庫端完成 filter、projection、order、pagination。
4. 用 generated SQL 確認實際 query shape。
5. 再檢查是否有 N+1、tracking 或 provider translation 問題。
```

## 工單狀態

商品搜尋已經不再先載入全部資料，但還沒有接到 MVC 頁面。下一張需求單是把這個查詢做成客服可以操作的頁面。

客服補了一句：

> 商品建立成功後，按重新整理，商品會多一筆。
